## 释放失败恢复

保持既有 RETRY_RESOURCE 动作，M3 OpenAPI 补充语义；无 M1 公共接口变更。当前独立验收人有区域权限且未参与维修，提供非空恢复理由，才可处理终态 FAILED + RELEASE_SOURCE + VERSION_CONFLICT。通过现有 GET /api/v1/internal/resources/sources，在本地事务外查询同一 M3 业务 ID，校验唯一记录、roomId、来源、版本以及活动来源类型为 MAINTENANCE。

随后锁定命令/工单、再次校验业务版本和权限，创建新的 operationId，sourceVersion 大于本地和来源当前版本；旧失败操作不修改。请求、动作审计、幂等结果与业务状态同事务持久化。新释放实际通过 M1 HTTP 完成，匹配回执后才 COMPLETED。对账后来源再次变化，M1 版本栅栏拒绝，仍保持安全阻塞；未伪称教室整体可预约。重复请求返回同一新操作，不重复释放。原验收时间继续用于累计验收耗时。

其他明确失败仍拒绝自动恢复；来源丢失/重复、房间不符、版本溢出、其他类型活动来源均拒绝。没有提供主管单人强制解除入口，未实现异常关闭。这里是针对已验收工单的来源恢复，不能代替正式授权管理或通用对账平台。

## 超时阶段事实

在 Act 和资源回执处理持有工单锁时，判断即将离开的旧阶段是否已超时且未记录；以旧阶段编号记录 m3_escalations，并追加 ESCALATE 审计。与后续动作任一写入失败即全部回滚。仍使用唯一 (workorder_id, stage_number, level) 和业务锁，避免扫描与动作重复。

资源开始按回执 effectiveAt 判断旧派单阶段结束，避免把网络回执延迟误算为迟到维修；验收阶段按实际验收申请时间计算，不将资源恢复等待纳入验收耗时。已结束阶段标记 OBSOLETE，保留统计和历史但不发送过时的主管待办。历史已漏掉的旧数据不自动猜测回填。

## 迁移恢复边界

MySQL 8.4 原子 DDL 仍可能在成功后、版本登记前进程退出。遇到 ADD COLUMN/INDEX 的重复对象错误（1060/1061）时，仅在临时副本中移除本语句新增对象并重新执行相同 ALTER，比对 SHOW CREATE TABLE 的规范化完整定义。定义一致视为该步骤已成功，继续后续 SQL；类型、默认值、顺序、索引等不一致则报错，不登记版本。

需要迁移账号拥有 CREATE TEMPORARY TABLES 权限。临时表连接私有，运行时业务表不会被删除列或重建。该机制覆盖现有 ADD 迁移；不声称自动恢复任意未来破坏性 DDL。新迁移应为复杂操作单独提供恢复设计。

### INT-04：维修影响事件 v1

正式候选契约：`contracts/resource-maintenance.openapi.json`。M1 在建立维修阻塞、补偿 M1 预约的同一事务写 m1_maintenance_impacts；只快照当时仍有效、尚未结束的 M2 ROOM 来源，记录精确 applicationId、applicationSourceVersion，以及 M3 来源、版本、生效时间和 correlationId。不直接读取或修改 M2 业务表。

M1 经真实 HTTP POST `/api/v1/internal/m2/maintenance-impacts` 投递，使用独立至少 32 字节服务凭证，禁止 Cookie 或复用 M2/M3 资源服务凭证。M2 以 eventId + 载荷摘要事务去重并持久化到 m2_maintenance_impacts，202 ACCEPTED 仅代表持久接收。同 ID 不同载荷返回 409。M1 投递最多自动尝试八次，未知结果仍使用原事件 ID；FAILED 可由 M3 服务通过查询与 retry 端点恢复，恢复操作写审计。

M2 自行锁定申请并核验房间、来源版本和事件生效时间。未来已批准活动取消，进行中活动终止；批准/释放结果未知时保留事件等待原操作核对。M2 写自身操作意图、审计和通知，通过现有 HTTP RELEASE_SOURCE 释放自身来源，确认前不提前标为终态。事件按 ID 分页消费，避免早期未决事件阻塞后续批次。服务重建后从数据库继续处理；旧事件只作用于快照活动，不影响维修后新批准活动。

本次只实现 ROOM_MAINTENANCE_STARTED。ENDED / ROOM_DISABLED 事件及通用主数据管理仍未实现，需求保持追踪；不将三种事件完整交付或人工跨组验收标为完成。失败释放沿用 M2 原有核对/重试入口，不提供强制删除其他来源的后门。

### INT-02：停用场地生命周期

M1/M2 房间模型新增可选 status，候选公开字段为 ACTIVE/DISABLED/RETIRED。显式状态优先；仅旧 active=true 兼容 ACTIVE，旧 active=false 为 UNKNOWN 并拒绝新增占用/阻塞，不自动解释为停用。M1 预约/整室占用只接受 ACTIVE；维修阻塞接受 ACTIVE 或明确 DISABLED，RETIRED 拒绝新增阻塞；已有来源仍可释放。释放来源从不改写生命周期。

开发目录的 M1/M2 与 M3 同一房间须配置一致状态。未增加生产主数据管理或自动迁移旧布尔值，正式主数据归属和映射仍待负责组评审。验收包括停用完整维修后仍不可预约、注销即使旧 active=true 也不得新增维修、其他来源保留。

## 启动变化

同时启用 `M2_ENABLED=true` 和 `M3_ENABLED=true` 时，在原后端启动环境额外设置：

```bash
export M1_IMPACT_SERVICE_TOKEN="$(openssl rand -hex 32)"
```

该值只放本机私有环境，不提交到仓库；需与 M2_SERVICE_TOKEN、M3_SERVICE_TOKEN 和开发用户凭证不同。只需在启动后端的终端设置；持久保存于已有私有启动配置后，重新载入即可。可选 `M2_IMPACT_URL` 指向同一 Go 应用地址，默认沿用 `M2_RESOURCE_URL`，例如 `http://127.0.0.1:8081`，必须和实际监听端口一致。前端启动方式不变。后端自动执行迁移 011；迁移账号还需 CREATE TEMPORARY TABLES 权限。先在隔离库验收再人工决定正式库升级，不手工改业务表。

仅启用 M3 时，M1 保留影响事件但不声称已投递 M2。原有 AUTH_DEV_PASSWORD 是开发种子配置，新增凭证与用户登录密码无关。
