# M3 开发任务与评审方案

依据：总约定 v0.2、需求基线 v0.4；起始 Git commit `b7f44e947639e005319e46ede4fde01182530a87`，现有分支 `feat/m3-reporting`。本文是开发方案，不是组内评审或人工验收记录。

## 当前代码与差异

- M1/M2 已有 Go/Gin、MySQL 迁移和 React 页面；M3 尚无业务实现。部分规划文件的“尚未实现”描述已经落后于代码，不能据此认定已有代码通过完整验收。
- D 身份/主数据仍是 `internal/dev` 适配器；公共审计、通知和任务库尚无正式接口。M3 不另建生产身份或第三套公共调度器。
- M1 `resources.go` 已实现维修阻塞/按来源释放/回执查询；没有正式资源 OpenAPI。当前资源端在阻塞事务内处理 M1 预约，而总约定描述可靠影响事件；M2 活动影响链路未交付。需 M1/M2/M3 评审差异，不能由 M3 自行选择并宣称 INT-04 完成。
- M3 上报允许停用空间；M1 当前创建阻塞会拒绝 `Active=false`。空间停用与维修阻塞的组合行为需要共同确认。
- `origin` 与 `upstream` 都指向 `CoffeeTau/campus-resource-platform`，尚未核实 fork 的父仓库；不直接更改远端。

## 第一步实现边界

纯业务状态机采用显式当前时间、权限、区域、当前维修人及历史维修参与人。每次转换返回新值，不修改传入对象；拒绝动作不产生副作用。资源操作分为“准备”与“回执确认”，准备中及未知状态禁止相反动作；超时不会释放资源。保存参数快照，重派不重置首次派单或维修时长，验收拒绝产生新阶段。

本步不注册 HTTP 路由、不执行迁移、不提供内存数据库替代 MySQL，不声称已实现事务、幂等存储、通知或重启恢复。API 认证和事务中的当前授权检查是后续应用层责任；请求 body 不能构造可信 Actor。领域规则本身不提供并发控制。

默认配置为 `proposal-v1`：描述 10–1000 字、派单/首修 4 小时、维修累计/待验收 24 小时、完成后 7 天评价。保留 DEC-07/08/09 待评审状态，不伪造实际参与者和决策。

## 下一步可评审的数据与契约方案

建议新增 `005_m3.sql`（实施前重新检查编号是否被占用），仅建立 M3 所属表：

- `m3_workorders`：报修人、空间/名称/区域快照、类别、描述、状态、版本、分派与接单、首次时间、累计时长、参数快照。
- `m3_commands`：操作者+幂等键唯一，保存规范请求哈希及结果；创建与动作同键异内容均拒绝。敏感动作在事务内锁定工单并检查 expectedVersion。
- `m3_assignments` / `m3_stages` / `m3_acceptances`：历次分派、阶段、处理结果及验收理由；历史参与人不得自验收。
- `m3_resource_operations`：稳定 operationId、M3 来源/工单 ID/递增 sourceVersion、请求、回执、重试时间和尝试数。HTTP 前提交本地事务；回执核对成功后再事务写业务结果。结果未知沿用同一请求和键。
- `m3_evaluations`：工单唯一，一次评价；无评价不进入均分分母。
- 审计/outbox 使用 M2/M3 共同确认的事务公共库；不先发网络通知再提交业务。不提前另造公共 schema。

拟定 M3 API v1：`POST/GET /api/v1/m3/workorders`、`GET /workorders/{id}`、`POST /workorders/{id}/actions`、`GET /m3/stats`。动作包括派单、接单、开始、完工、拒绝验收、验收、取消、评价。写请求带 Idempotency-Key，动作带 expectedVersion；准备/恢复返回 202，不提前宣称生效。列表默认本人，区域及待办须服务端授权，稳定分页。

资源侧沿用总约定 v0.2 的 `BLOCK_ROOM_MAINTENANCE`、`RELEASE_SOURCE` 和回执查询，M3 不改 M1/M2 内部表。正式 OpenAPI 由 M1 维护，M3 提供成功/失败/未知结果测试案例；来源、成功界点及重试方案须双方确认。

待评审：M3 schema、D 认证/空间/审计/任务/通知的进程内契约、资源正式契约、INT-04 影响事件及停用空间行为。未评审前只完成独立规则及可审查方案，不把公共契约自行定稿。
