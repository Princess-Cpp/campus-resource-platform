## GAP-01：停用空间可报修，但 M1 不接受新增维修阻塞

需求：M3-01.1、M3-01.3、INT-02。提供边界：M2 的主数据生命周期、M1 的资源操作；调用边界：M3。

现状：`docs/requirements/m3.md` 允许停用但仍需维修的空间上报，禁止注销空间新增工单。M3 目录区分 ACTIVE/DISABLED/RETIRED；M1 `booking/resources.go` 对非释放操作统一检查 `Room.Active`，因此 DISABLED 时 BLOCK_ROOM_MAINTENANCE 的回执为 FAILED / RESOURCE_UNAVAILABLE。M3 保持 ASSIGNED，不虚报 IN_PROGRESS；`TestRepairExplicitBlockFailureCanDeliberatelyStartAgain` 已通过真实 M1 HTTP 验证拒绝后的安全状态。它验证安全失败，**不证明停用空间维修业务已完成**。`TestRepairReleaseDoesNotEnableDisabledRoom` 验证维修后停用的空间不会被释放误启用，是另一个案例。

建议评审方向：先由主数据/资源提供方明确 DISABLED 与 RETIRED 的公开生命周期语义，再决定“停用仍允许维修阻塞”或其他合法工作流。不要由 M3 把 Active 改成 true，也不能仅凭 M1 的一个布尔值自行放行注销资源。修订公开资源契约、错误语义和提供方测试后，M3 对接和验收；停用标记的解除仍归主数据负责人。

|联合案例|预期出口（需评审后锁定）|当前状态|
|---|---|---|
|J-01a 停用空间新增报修|合法访问者可报修；注销空间拒绝|报修校验已有实现/自动测试；本轮浏览器未演示停用空间|
|J-01b 停用空间开始维修|按确认后的生命周期协议处理；绝不为维修自动启用场地，不将 FAILED 当 CONFIRMED|当前资源端拒绝；跨组业务阻塞未解决|
|J-01c 停用空间验收释放|只释放工单来源，停用仍然阻止预约|真实 HTTP 自动测试通过；联合人工 not_run|
|J-01d 同键重放/改键重试/目录变化|相同操作回执稳定；明确失败后的新尝试使用新操作，注销/权限变化不能被绕过|已有失败/重试自动测试；修订后仍需双方契约与 HTTP 验收|

## GAP-02：维修对 M2 已批准活动的影响尚未接通

需求：INT-04、M3-01.3、INT-02/03。M3 牵头协调；M1 维护资源事实与本模块预约处置；M2 维护活动申请的业务处置。不能将全链路缺口归为 M3 单组代码缺陷。

现状：总约定要求可靠影响事件（ROOM_MAINTENANCE_STARTED / ENDED / ROOM_DISABLED）与消费回执，具体路径及顺序协议仍待双方评审。当前 M1 确认维修阻塞后在自身事务内处理 M1 预约；M2 `classroom/http.go` 和 `contracts/m2.openapi.json` 没有供维护影响事件消费的入口。现有人工动作 TERMINATE 需 classroom.terminate、区域权限、APPROVED、活动已开始且未结束、非空意见，不能由 M3 假扮审批人调用来替代维护影响协议，也不能覆盖尚未开始的已批准活动。

本轮不新增私有猜测的事件端点，不直接写 M2 的申请、来源、通知或审计表。现有“释放保留其他 M2 来源”测试只证明来源保护，不等于 M2 活动已经自动取消/终止并通知。

|负责边界|评审/实施交接项|完成条件|
|---|---|---|
|M1/M2/M3共同|事件版本、服务身份、eventId/roomId/sourceModule/sourceBusinessId/occurredAt/sourceVersion、影响时间范围、成功界点、回执、重试和乱序规则|同步总约定、正式 OpenAPI、调用方与双方测试；记录真实评审结论|
|M1资源事实 / M3调用|确定事件从确认资源事实的哪一方可靠产生，持久化投递与核对，重启可补扫|不能只在浏览器或一次内存回调中发送；不因通知失败重放业务动作|
|M2接收|自行决定并实现未来活动/进行中活动的维护处置，保留批准历史、原因、审计和通知；按来源释放本模块占用|M2业务状态与实际不可使用一致；不是由 M3 跨写申请表|
|M3联调|按冻结版本接入发送/回执/恢复，与 M1/M2 验证全链路|真实 HTTP + MySQL，记录工单/事件/来源/回执，不能用单模块 mock 测试替代|

联合验收 J-02a：先批准一个未来活动，再开始维修，场地立即阻塞；M2 按评审政策反映不可正常使用并通知，保留批准历史。J-02b：进行中活动同理，但结束/终止原因正确。J-02c：同一事件重复投递、丢失响应、消费后重启，不重复处置/释放/通知。J-02d：结束事件先到、旧开始事件迟到，不影响维修之后合法新建活动。J-02e：两张工单/M2来源共存时只释放自己的来源，全部维修结束仍检查停用与活动占用。J-02f：越权服务或伪造来源拒绝，不能调用工作人员动作绕过协议。

J-02a至J-02f 的维护影响消费全链路均为 **not_run / 外部契约与提供方实现待完成**。目前可用的证据仅限已实现的资源阻塞、来源隔离与正常维修闭环；本轮不得把本文当作双方已经通过的联调记录。
