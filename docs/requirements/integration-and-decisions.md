# 跨模块集成与待定决策

三组共同的模块边界与接口设计入口为 [模块设计与集成总约定](../architecture/module-design-and-integration.md)；本文保留本主题的详细说明，公共接口调整须同步总约定。

本文定义集成业务效果；接口评审、分别实现、失败处理和联调流程见 [模块协作与集成开发](../process/module-collaboration.md)。

## INT-01 整室审批写回

方案与联调主责：M2，资源一致性评审与实现：M1。

M2 最终审批 → 资源公开 HTTP 创建 M2 来源区间占用 → 原子仲裁与幂等结果 → M2 记录 APPROVED → M1 搜索与提交均排除目标区间。驳回和待审批正常情况下无占用；仍需处理未知请求结果的残留。撤销、到期、紧急终止只能释放自己的来源。

仲裁须携带申请版本、deadline、操作标识；不能只在 M2 发送前检查到期。资源写入和最终批准逻辑需要统一成功界点：建议资源事务以权威 now < deadline 确认决定并保存回执，M2 对账采用该回执，若未在截止前确认则到期并释放。超时扫描必须等待/核对正在确认操作，不在已有效确认的申请上盲目 EXPIRED。版本和终态释放栅栏防止迟到请求复活。此方案由 M2牵头收敛、M1评审并共同验证，不是假设 HTTP 具有跨库事务。

验收：批准与个人预约并发无双占；批准回执丢失后恢复；开始前到期与确认竞争无超时来源残留；撤销响应丢失后不清掉其他占用；观察真实网络调用和座位写回。

## INT-02 维修下架与恢复

M3 开始维修 → 资源 HTTP 创建 M3 来源持续阻塞 → 确认后 IN_PROGRESS → M1 禁止新预约。验收待处理期间保持阻塞；验收确认 → 仅释放该工单 → M3 完成。多工单和 M2 来源共同决定可用性，不能以“最后完成的一张工单”覆盖整个教室的历史状态。

建议在阻塞生效后发布维修影响事件，由 M1/M2 各自取消或终止受影响记录。事件具备 ID、工单来源、发生时间和资源范围；原模块自行持久化幂等处理、免违约、通知及审计。M3 不直接访问预约数据库。尚未验收不得因为预计完工时间自动解除维修阻塞。

验收：两个工单先后维修、先完成一个仍不恢复；恢复后仍存在 M2 区间占用/管理员停用；影响事件重复和中途崩溃可恢复；已签到学生不被维修取消误记违约；真实 HTTP 集成具备来源证据。

## INT-03 来源追溯

从座位可用性解释关联到 M1 预约/M2 申请/M3 工单，再由 correlationId 关联操作和审计。一般学生仅看到“整室活动占用”“维修中”等原因，不查看其他用户个人信息。授权管理人员可按来源 ID 查询对应详情，权限仍由源模块决定。

验收：三种来源分别出现和释放；多个原因共存可解释；历史来源不因注销或改名丢失；未授权用户无法利用来源链接越权。

## 补充集成：INT-04 停用、维修对既有使用的影响

唯一联调牵头：M3；M1/M2维护本模块业务处理，M2提供主数据停用支持。

D 强制停用或 M3 阻塞与 M1 的签到、迟到扫描、M2 的活动状态共享一致的终止原因。维修导致取消不算违约；M2 原批准保留审计但不能继续显示可正常使用。个人预约和整室申请的普通竞争默认先成功者保留，只有安全维护和授权紧急停用走强制补偿。

验收：维修取消与迟到扫描并发不会新增错误违约；已经错误新增时补偿更正且留审计；整室已开始活动显示被中断并通知；阻塞恢复不自动复活已取消预约，学生重新预约并重新仲裁。

## 待决定政策

| 决策 ID | 提案 | 备选与影响 | 需参与者 |
| --- | --- | --- | --- |
| DEC-01 | 采用 MySQL；后端最新为 Go + Gin，前端 React + Vite | 小时槽与事务仲裁需验证整室并发；部署已确认为同仓库、单应用 | 三组 |
| DEC-02 | 按 D 子域分配责任 | 单组承担 D 接口集中但可能过载；分摊需契约治理；D-02转M2、明确公共库与发布角色，先估算后确认 | 三组 |
| DEC-03 | M2 单独申请权限、院系+场地两级、不同人员 | 全员申请更易用但治理不同；一级不满足多级要求；更复杂流程增加成本 | M2、D |
| DEC-04 | 待审批不占位、最终冲突拒绝 | 提交即锁占可能大量占座；优先驱逐个人预约涉及公平性与申诉 | M1、M2 |
| DEC-05 | M2 默认最长4小时、提前14天、24小时审批期限 | 不直接继承 M1 参数；不同活动时长和审批工作时间需确认 | M2、场地代表 |
| DEC-06 | 维修开始取消/提前终止既有使用、免违约 | 仅禁止新预约不保证安全；必须讨论已签到人员和整室活动通知 | 三组 |
| DEC-07 | 场地管理员验收，不能参与该单维修 | 报修人验收可能长期缺席；物业自验收缺少职责分离 | M3、场地代表 |
| DEC-08 | 4小时派单/开始、24小时维修/验收，自然时计时 | 工作日计时复杂且需日历；不同严重程度可后续分级 | M3 |
| DEC-09 | 评价7天内一次不可改 | 可修改更易纠错但需版本；不能允许物业改学生评分 | M3 |
| DEC-10 | 开发本地账号、生产认证待明确；至少真实邮件推送 | 校园SSO/微信依赖凭证；不能拿站内消息冒充外部推送 | D 负责人 |
| DEC-11 | Asia/Shanghai 展示、统一时间点存储 | 跨时区日界线影响每日签到码和开放规则 | 三组 |
| DEC-12 | 数据保留、申诉和纠正按课程与隐私需要定期限 | 永久保存造成风险；过早删除无法验收或申诉 | 三组 |

每项记录真实参与者、备选、依据、决定、日期和影响需求；DEC-01 的技术栈按用户选择记录，其余政策仍待评审。

## 按三组估算工作量

M1 已有详细需求，但还需边界与集成分析；M2/M3 补需求本身计入工作。估算单位建议为人日区间，先分解需求澄清、后端、前端、测试、公共能力和集成；不要先凭功能数得出某组必然较轻。业务状态机、资源并发、超时与恢复分别单列。D 责任只有在估算后确定，工作量表暂不填虚构数值。
