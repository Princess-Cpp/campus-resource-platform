## 共用定义

- 业务时间显示建议 Asia/Shanghai；持久化时间为统一时间点，接口必须带时区；区间 [start,end)，相邻时段不冲突。
- 截止判断使用服务端权威时间，now >= deadline 即到期，客户端时间不能延长期限。
- 请求人身份取自登录凭证，不信任 body 中的 userId；角色权限还须结合院系、区域、记录归属。
- 业务状态与跨模块同步状态分开保存；网络超时只表示结果未知，不能直接认定失败或重发不同操作。
- 需求 ID 沿用原计划的父级编号，细化为 M1-01.1、M2-01.1 等；原编号不删除。D-04 起为新增公共能力。
- 下文每个编号需求的“验收”即验证目标。当前全部为未实现、未运行测试；实现后在 baseline.json 填实现文件、测试文件和当前运行证据。
- 采用 MySQL；前端 React + Vite，后端最新选择 Go + Gin；同仓库、单应用部署已确认。

## 基线与扩展

先阅读 [范围分级](scope.md)：每条需求的基线和加固范围在索引分别记录，必要正确性不降级。

基线：三个业务闭环、D 公共能力、两条跨模块写回及来源追溯。审批采用两级作为提案，不要求任意工作流设计器；通知至少一个真实投递渠道，开发环境可使用邮件接收服务。移动端原生应用、智能派单、附件视频、单座位维修、任意审批流程编辑器属于扩展，不默认加入三组工作量。

## 验收方法

API 行为、数据库持久化、并发、可控时钟、重试与实际 HTTP 集成均需对应验证。权限测试同时覆盖“缺少动作权限”和“有权限但超出数据范围”。关键测试做破坏性验证，例如临时移除来源过滤或冲突检查，观察测试失败，然后恢复实现重新执行。文档校验不等于业务验收。
