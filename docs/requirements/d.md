# D 公共层需求

状态：待评审。D 是公共能力集合，不是必须成立的第四个模块组或必须单独部署的一个服务。本文件定义能力与责任边界，三组如何分摊仍需比较工作量后形成真实决策。

## D-01 身份与权限

### D-01.1 账户与登录

基线角色：学生/申请人、院系审批人、场地管理员/审批人、运营管理员、物业调度员、维修人员、验收人、物业主管、系统管理员。角色可叠加，职责分离仍由业务模块强制检查。用户包含内部稳定 ID、学工号、姓名、院系、账号状态和通知联系方式；学工号唯一，院系不得由用户自行修改取得额外权限。

无校园统一登录条件时采用本地账号作为开发基线，生产登录方式待确认；不硬编码默认生产密码。密码只保存安全哈希；登录错误不泄露账号是否存在。登录建立有期限的会话、支持退出，暴力尝试限流；禁用后既有会话也不能继续操作。角色变更不得靠重新登录才生效，写操作使用当前授权信息。

验收：重复学工号不能建号；错误密码登录失败；过期或退出会话不能操作；禁用后已登录会话失效；学生不能改变院系/角色；日志不出现密码、会话令牌；种子账户只能用于明确的开发环境。

### D-01.2 动作权限与数据范围

RBAC 至少支持用户-角色、角色-权限；权限按动作命名，例如 room.read、seat.manage、booking.create、classroom.apply、approval.department、approval.final、workorder.dispatch、workorder.repair、workorder.accept、audit.read。每个动作同时检查数据范围（本人、院系、授权区域、全校），默认拒绝。

角色配置可修改但不能删除仍被引用的角色而造成悬空权限；操作版本和审计可追溯。系统管理员不得把权限授予行为当成普通业务审批，业务职责分离单独验证。禁止通过客户端传入 scope 或角色名扩大范围。

验收：有审批动作权限但不管辖场地仍不能批准；有维修权限但未派给本人的工单不能修改；查看本人历史不能查看他人；角色撤权后下一次敏感操作被拒绝；列表、详情、导出和附件采用一致的数据范围。

### D-01.3 角色与权限管理界面

系统管理员可启停账号、配置角色、赋权及范围；显示变更前后差异与影响提示。保留至少一个有效系统管理员，防止误操作锁死系统；紧急恢复走记录化的受控流程，不以手工改库为常规功能。审批人、调度员与验收人的业务指派由各模块/管理员按授权完成。

验收：普通用户访问管理 API 被拒绝；最后一个管理员不能被直接移除；赋权范围超过操作者可管理范围失败；每次授权变更有审计；权限变更不会伪造过去操作者的角色。

## D-02 空间、座位与配置

### D-02.1 空间主数据

空间字段：稳定 ID、名称、校区/楼栋/楼层、容量、所属院系或全校开放、用途、状态（ACTIVE/DISABLED/RETIRED）、开放时间规则。座位字段：稳定 ID、教室 ID、室内唯一编号、插座标记、状态。容量不等于座位数，可供 M2 使用，M1 使用实际启用座位数。角色有权查看的空间才显示在搜索中。

有历史引用不能物理删除空间或座位，以注销标记停止新业务；重新启用保留同一身份与历史。修改教室座位构成不得使已批准整室占用失效，新座位同样继承该室的有效区间占用与维修阻塞。

验收：同教室座位号不能重复，跨教室可重复；跨教室引用座位失败；注销后不接受新预约但旧历史可查；增座后该时段整室占用仍覆盖新增座位；未授权用户不能维护其他区域资源。

### D-02.2 开放规则与停用

支持每周开放时段、指定日期例外、全校/院系访问规则；例外优先于每周规则，闭馆区间不可预约。跨日区间逐日校验。配置维护与维修阻塞独立保存，恢复维修不能把管理员停用恢复为 ACTIVE。

存在未来有效预约或已批准整室使用时，普通管理员修改开放时间/停用默认拒绝并展示影响数量；确需紧急停用走有权限的强制操作，说明理由，触发 M1/M2 取消或终止及通知，免记学生违约。注销亦遵循影响处理，不以状态标记掩盖残留预约。

验收：例外闭馆覆盖周规则；关闭后不存在可新预约时段；普通修改影响预约时失败；强制停用先阻止新预约、补偿旧记录可重试；维修恢复后仍停用的教室不开放；历史保留变更版本。

### D-02.3 业务参数

参数按模块命名和版本管理：M1 时长、签到与提醒；M2 申请窗口、时长、审批期限；M3 派单/维修/验收时限和评价窗口。每次改动校验类型与范围并记录生效时间；已创建业务保存适用参数，不能回溯把原合法预约判为违约。界面清楚区分默认、当前值及适用范围。

验收：负时长、互相矛盾的提醒阈值、无权限变更均失败；修改 M2 时长不改变 M1 参数；历史可查适用版本；重启参数仍在 SQL 中持久化。

## D-03 通知与操作审计

### D-03.1 通知投递

业务模块提交含 eventId、业务类型/ID、接收对象、模板版本、允许展示字段的通知事件。基线提供站内通知和至少一种外部渠道（建议邮件）；开发邮件接收器能验证真实投递，不宣称已发至公网邮箱。按接收者与事件去重，业务事件可靠落库后异步发送，失败有次数、下次重试时间与原因，达到上限进入人工可见失败队列；网络不明时不无限新增消息。

站内以 eventId+接收者保证一条逻辑消息；外部渠道通常至少一次投递，响应丢失可能重复，不能承诺不可验证的“绝不重复邮件”。若渠道支持幂等键则使用。取消/过期预约后不再发送旧签到提醒；发送前向源模块核对适用状态或使用有效的失效标记。

验收：业务提交成功但邮件失败时业务状态保持；业务事务失败不产生通知；重试只存在一条站内消息；坏地址记录失败且可诊断；已取消预约的未来提醒被抑制；通知不能包含密码/会话令牌，也不能让收件人越权打开详情。

### D-03.2 站内通知与偏好

用户看本人消息、未读数、标记已读；不能更改他人状态。区分必要业务通知与可关闭的运营信息；更改邮箱需验证归属。必要取消、维修、审批结果不允许通过关闭营销偏好丢失。未配置外部渠道时显示能力缺失，至少站内可用；完成课程推送验收仍需实际渠道。

验收：读取他人通知被拒绝；重复标记已读幂等；读通知不泄露业务详情；偏好关闭不屏蔽必要业务事件；邮箱验证未完成不能发送敏感业务详情。

### D-03.3 操作审计

记录 auditId、操作者（用户或服务）、动作、模块、业务 ID、来源、原/新状态摘要、结果、理由、权威时间、correlationId。覆盖身份权限、资源配置、预约/审批/工单关键状态及强制操作；权限失败留下安全事件，避免将敏感内容完整写入失败日志。

关键业务与本地审计事件在同一事务持久化，统一汇聚服务暂不可用时可重传，不能丢记录；审计对普通业务接口只读，不允许客户端篡改。仅授权审计员查询，按院系/区域限制，分页导出脱敏；日志不记录密码、完整令牌、动态签到码或无关联系方式。

验收：成功状态变更对应唯一审计事件；业务回滚不生成虚假成功记录；汇聚失败后恢复能补齐；跨模块 correlationId 可串联批准与资源写回；未授权读/删/改审计失败；并发顺序以版本和事件关系可解释。

## D-04 统一资源可用性与来源追溯

### D-04.1 可用性判定

逻辑公共能力由单一责任方维护，建议位于 M1 资源接口，而不是让各组各写一套。输入用户范围、空间/座位和时间区间，综合空间/座位启用、开放规则、院系限制、M1 个体占用、M2 整室区间占用、M3 持续阻塞。返回不可用原因集合与有权限的来源摘要，不能只返回一个互相覆盖的 seat.status。

查询是快照，最终写入必须重新原子仲裁。M3 可以叠加多个维修阻塞；阻塞优先禁止新预约但不删除 M2 历史来源。判定必须能解释当前为什么不可用且不泄露其他学生信息。

验收：M2 只阻止相交区间；M3 所有座位不可新预约；不在开放时段、院系不符均失败；查询可用后被别人占用，提交仍拒绝；多个原因同时存在都能追溯；新增座位同样遵循房间级限制。

### D-04.2 占用、阻塞与释放

来源字段：sourceModule=M1/M2/M3，sourceBusinessId、resourceScope、区间或持续阻塞、operationId、状态、写入时间及请求版本。M1 创建个人占用，M2 创建整室占用，M3 创建维修阻塞；网络调用经过服务身份鉴权，M2 不得伪造 M3 或释放 M1 来源。

同一幂等键同内容返回原结果，同键不同内容拒绝；相同来源释放多次为幂等成功。写入采用数据库事务和明确锁定顺序，整室与个人占用覆盖同一仲裁范围；不能只有“先查再插”。查询接口能核对操作是否生效，释放记录不能被迟到旧创建重新激活，具体实现须有来源版本/栅栏或等效保证。

验收：并发重叠请求无双占；整个教室占用不会只写一半座位；多个工单各占独立来源；释放工单 A 不动 B、M2、管理员停用；非法服务来源被拒绝；先释放再收到旧创建不复活阻塞。

### D-04.3 对账与异常恢复

源业务模块周期核对自身待处理操作与资源结果，资源侧可列出授权来源的有效占用；以终态和版本解释残留。失配进入可见异常队列，重试、补偿、人工授权处置均留审计。管理员不能通过“一键清空教室全部状态”恢复。

验收：业务进程在资源成功后崩溃，重启恢复正确业务状态；已撤销/超时来源残留最终释放；实际仍维修的来源不被错误清除；人工异常处理不得跨来源越权；恢复任务多次执行结果一致。

## D-05 契约与工程公共要求

### D-05.1 公开接口与错误语义

维护 OpenAPI 或等效版本化契约，定义请求/响应、时间格式、分页、业务错误和幂等重试；身份/权限错误与输入不合法、资源冲突、版本冲突、结果待确认、依赖不可用分开。响应 correlationId 用于排查。接口不直接暴露数据库实体或任意 SQL 查询；跨模块不共享可写数据库凭证。

验收：M2/M3 按公开 HTTP 契约实际调用资源能力；契约测试校验字段和错误；敏感字段不出现在公共响应；不兼容接口变更不能未经评审直接发布；日志可关联整个调用链。

### D-05.2 SQL 迁移、种子与运行配置

各模块按归属维护版本化迁移，公共层变更共同评审；空库到最新可一次重放，重复启动不重放已执行版本。种子按稳定键幂等，主数据/开发账户与真实业务数据分离；生产不自动注入测试用户和弱口令。运行配置、凭证、日志与源码分离。

验收：空 SQL 库完成迁移后 M1/M2/M3 可运行；二次执行无重复种子；schema 更新不破坏历史引用；测试数据不会进入生产；数据库恢复/回滚按发布方案实际演练，不承诺破坏性迁移可自动逆转。

### D-05.3 健康、任务与数据治理

提供存活与就绪检查，就绪检查依赖数据库/迁移及该服务必要条件；返回最少信息，不公开凭证。后台任务多实例竞争需防重复，能观测漏跑、失败和积压。备份、保留期和清理规则作为部署评审项；业务、通知、日志和审计分别配置，不无限保留学生数据。

提案：课程开发仅用虚构种子；已结束业务保留至课程验收与申诉窗口结束，具体期限待组内决定。访问、更正与违约申诉留痕，不通过删审计掩盖纠错；修正事件关联原记录。

验收：数据库不可用时就绪失败；服务进程存活不被误判业务可用；多个任务执行者只完成一次逻辑迁移；备份恢复后历史可追溯；清理任务不删除仍待审批/维修/申诉记录；个人更正不破坏必要审计。
