## 角色与可见业务

下表按**有效权限**解释现有实现，不新增、暗授或替团队确认角色。多角色用户取已授业务权限的组合，同时仍受院系/区域/本人归属、工单状态与职责分离约束。学生账号如另外得到显式工作人员授权，就是多业务身份；仅有普通学生权限的账号不能操作工作人员功能。

|角色/权限|应显示或允许的业务|不能因该角色自动取得的能力|
|---|---|---|
|普通学生/报修人|M1 搜索、本人预约/签到/取消与消息；另具课堂申请权限时 M2 申请及本人记录；另具报修权限时 M3 报修、本人记录、早期取消、完成后一次评价和本人消息|M2 审批/统计；M3 区域列表、派单、维修、验收、升级与统计；任何内部资源服务操作|
|M2 院系审批人 `approval.department`|审批待办，本院系授权申请的第一级审批，禁止自审批|最终审批、统计、其他院系业务、M3工作人员能力|
|M2 场地审批人 `approval.final`|授权场地的最终审批；另具 `classroom.terminate` 时依照时间/状态和意见要求终止活动|跳过前级、自审批、M3验收或派单|
|M2 运营管理员 `classroom.stats`|申请统计中的授权范围聚合|申请详情、审批、M3统计（需要独立的M3权限）|
|M3 调度员 `workorder.dispatch`|区域调度台，授权区域查看、派单、重派给当前有效且覆盖区域的维修人|维修、验收、统计、主管升级权限|
|M3 维修人 `workorder.repair`|维修待办；当前分配给本人且仍有区域权限的工单接单、开始维修、提交完工|他人工单、重派、维修中普通取消、本人或曾参与工单的验收|

## 菜单、页面与服务器三层检查

1. **菜单**：M3 取已登录身份对应的 `/m3/session` 有效权限；M2 取公共会话已授的申请/审批/统计权限。侧栏与工作台共用筛选。匿名、切换账号的旧响应、加载失败、未知入口不放行。
2. **页面**：M3 工作台直接输入 URL 也检查对应权限，没有权限时不挂载业务工作台；工单详情依赖服务端归属检查。M2 本轮只修改共享导航展示，直接访问页面仍由其既有 API 检查，未改 M2 内部规则。
3. **服务器**：每个请求使用当前身份，校验当前权限和区域/院系/本人归属。M3 动作使用服务端 `allowedActions`；修改请求仍独立检查，不信任菜单、角色名称、客户端权限、请求中的用户ID或历史重放结果。

当前检查未发现可复现的“普通学生使用自己的会话执行管理员/工作人员动作”绕过。实际修复了菜单暴露、M3 页面入口缺少前置提示、业务页面中的开发措辞，并另外修复下述内部服务凭据配置风险；不将原来的菜单可见性问题夸大为已能写入管理员业务，也不声称穷尽所有安全风险。
