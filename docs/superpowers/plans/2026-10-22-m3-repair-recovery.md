# M3 第三轮：维修下架与独立验收恢复

基线：`359f0b7a40596c714e373d058e1fed6aa5f83ba6`，分支 `feat/m3-reporting`。依据模块设计与集成总约定、M3 需求及 scope.md；沿用已有 M1 v1 资源 HTTP 契约。本轮本地实现和验证，不自动提交、推送或合并。业务默认值及迁移编号仍为待评审提案。

## 方案和允许改动范围

仅改 M3 后端、页面、M3 契约和验收记录；新增版本化迁移 008，保存 M3 的资源操作，不改已执行迁移和 M1/M2 内部数据。应用启动接入 M1 服务凭证和固定地址，浏览器不接触服务凭证。资源调用先提交本地操作，再真实 HTTP 请求；业务事务不跨网络持锁。回执核对操作 ID、模块、业务 ID、来源版本、状态、时间，成功后同事务保存工单、回执、审计及 outbox。

## 状态和权限

|动作|权限与归属|前置状态|结果|
|---|---|---|---|
|开始维修|当前已接单维修人|ASSIGNED / IDLE|先 PENDING，M1 下架回执确认后 IN_PROGRESS|
|完工|当前已接单维修人|IN_PROGRESS / IDLE；必填处理结果|AWAITING_ACCEPTANCE，保留下架|
|验收驳回|辖区验收人，排除所有历史维修参与人|AWAITING_ACCEPTANCE / IDLE；必填原因|IN_PROGRESS，保留下架|
|验收通过|同上|AWAITING_ACCEPTANCE / IDLE|先 PENDING，M1 仅释放本工单来源后 COMPLETED|
|继续核对|原动作对应的当前权限|未知结果的同一操作|重用操作 ID、来源版本和请求，不创建第二个来源|

超时、无效回执及重启均不推定操作失败或阻塞消失；自动重试耗尽转 NEEDS_ATTENTION，仍保留操作。明确的下架失败可重新发起开始维修；明确的释放失败保持待人工处理，禁止伪造恢复成功。

## 数据与公共依赖

新增 `m3_resource_operations`：操作 ID、工单 ID、来源版本、不可变请求、发起者/幂等键/关联 ID、状态、尝试数、下次执行时间、错误、回执及时间。工单既有快照保存状态、维修参与人、阶段、处理结果及耗时；既有事件保存每轮验收意见；不另造 M1 来源表。业务命令、操作、审计、outbox 在同一 MySQL 事务提交。工作者使用连接级互斥防止并发发送，同一操作可重查。

M1：POST/GET `/api/v1/internal/resources/operations`，`BLOCK_ROOM_MAINTENANCE` / `RELEASE_SOURCE`，`sourceModule=M3`、`sourceBusinessId=工单ID`、单调来源版本；复用操作 ID 作为资源幂等键。M2：不直接改审批/活动数据。身份使用现有 SQL 会话；验收人员暂用显式开发绑定，不写公共角色。目录和事务事件仍为既有开发适配器，正式公共适配与送达不能标为完成。

## 待确认与边界

- 公共 schema/迁移编号和公共适配器仍待组内评审，本轮不得记录为已批准。
- M1 当前对已有个人预约执行自身取消逻辑；与总约定的可靠影响事件差异继续记录，M3 不越界改写。
- M2 活动受维修影响的联动、正式通知送达、超时升级、评价、统计及部署不属于本轮完成范围。
- 禁用教室可报修，但现有 M1 拒绝对非 active 教室新增维修阻塞；按真实失败回执呈现，不擅改 M1。
- 明确释放失败需要协调来源版本/资源端原因；不通过手工改库或伪造新成功回执解决。

本轮将已有领域规则接入持久化应用和页面；新增测试必须执行实际业务，不以常量断言或替代资源业务逻辑的模拟宣称集成完成。
