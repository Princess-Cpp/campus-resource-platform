# M3 派单与接单实施计划

> 执行方式：按用户“继续下一轮”及此前按已有约定直接推进的授权，由当前会话逐项实现；不自动提交或上传，不创建新分支，不要求重复批准既有方案。

Goal：让已持久化报修经过区域调度派单、重派、维修人接单及本人早期取消，所有操作通过真实 HTTP/MySQL。
Architecture：复用 maintenance/domain.Order.Apply、统一 Cookie/CSRF、共享连接池与现有 Events 事务端口。新写操作先锁幂等命令再锁工单，当前权限/范围/归属有效才重放旧结果；首次执行核对 expectedVersion。开发身份映射只配置真实已注册的虚构用户 ID，不改 D 内部数据。
Tech Stack：React/Vite/TypeScript、Go/Gin、MySQL。
Spec：docs/requirements/m3.md 的 M3-01.2、M3-01.5、M3-01.7、M3-02.2；docs/architecture/module-design-and-integration.md v0.2；已有 docs/superpowers/plans/2026-10-22-m3-next-steps.md Task 3。起点 a994d3f61af2ac6d1b362c666e89cb63ef8dc44b，分支 feat/m3-reporting。

## 约束与受影响契约

- 只扩展 M3 API/OpenAPI、M3 SQL、M3 页面及必要应用装配；不改 M1/M2/identity 实现或其业务数据。schema 与公共适配器仍待团队 review。
- POST /api/v1/m3/workorders/{id}/actions：action=ASSIGN/ACCEPT_ASSIGNMENT/CANCEL、expectedVersion、assigneeId（仅派单）、comment；Idempotency-Key 必填；不接受客户端权限、身份、资源操作或未来动作。
- GET /workorders?view=mine|dispatch|assigned：本人、当前授权区域调度、当前维修待办；仍支持稳定分页/原有筛选。GET 详情以领域 CanRead 授权，不让旧维修人因历史分派继续读取他人工单。
- GET /workorders/{id}/assignees：当前调度权限+区域范围，返回当前启用且拥有该区域维修权限的人员最小信息。目录使用 identity.Store.Principal/Principals 公开方法，不查 D 内部表。
- 007_m3_dispatch.sql（本地候选编号）：增加工单 assignee_id/待办索引、m3_assignment_history；事件 comment；outbox 主键扩展为事件+收件人+类型，支持新旧维修人分别收到不同意图。006 不改。
- 接单维持 ASSIGNED，只保存 acceptedAt；不提供 START/FINISH/资源下架。未实现、未投递与待评审保持可追踪。

## 重点边界

1. 同键重试、丢包后刷新、服务重建：复用原始动作、版本、目标、键；成功结果不能触发第二次历史/通知。前端未知结果保留到会话存储，禁止编辑成另一动作。
2. 两名调度员同版本派单：仅一人成功，另一人 409；同键不同动作/不同工单同样拒绝。
3. 维修人员被禁用/撤权/不在区域，或在候选列表加载后失效：提交时重新读取可信目录并拒绝，不信任下拉框缓存。
4. 重派后旧维修人立即失去详情及接单权，首派时间/阶段期限不重置；旧人只保存一次交接通知意图。
5. 事务事件失败、取消与派单/接单竞争：工单版本、分派历史、命令结果和 outbox 全部一起提交或回滚；取消终态不再派单。
