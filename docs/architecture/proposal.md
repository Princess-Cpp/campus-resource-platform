# 架构提案

三组共同的模块边界与接口设计入口为 [模块设计与集成总约定](module-design-and-integration.md)；本文保留本主题的详细说明，公共接口调整须同步总约定。

## 当前技术选择

| 层次 | 用户选择 | 待明确项 |
| --- | --- | --- |
| 前端 | React + Vite | UI 组件库与版本 |
| 后端 | Go + Gin | Go 与 Gin 版本 |
| 数据库 | MySQL，满足 SQL 要求 | MySQL 8.4 LTS 为提案 |
| 仓库与部署 | 同仓库、单应用部署（用户已确认） | 构建、HTTP 契约和发布脚本待实现 |

用户已选择 React 前端与 Go + Gin 后端。生产由 Go + Gin 提供 Vite 构建产物和业务 API，发布一个应用包；开发时 Vite 可独立运行并代理后端 API。

会话、提醒与通知任务、幂等键和重试事件采用 MySQL 持久化。任务领取与并发仲裁通过数据库事务、唯一约束和数据库锁实现，并验证重启/多实例行为。

共享代码只包含基础工具和接口定义，不能通过公共代码直接访问其他模块内部仓储。D 按子域分配，不额外成立第四模块组。跨模块须保留真实网络接口验收：M2/M3 使用专用 HTTP 客户端调用同一应用内的资源公开 API，目标地址由运行配置提供，不直接改写资源表。调用携带服务身份、幂等键和 correlationId；本机 HTTP 仍为真实网络调用，不是进程内函数调用。数据库事务不能跨 HTTP 调用等待；先保存操作再调用，按结果确认和对账，避免持有锁造成自调用死锁。此结构无需为每个模块部署独立服务。

## 目录与部署

计划结构（尚未创建应用脚手架）：

```text
frontend/                         React + Vite，按 M1/M2/M3/D 组织页面
backend/                          一个 Go + Gin 应用
  cmd/server/                    应用入口与启动
  internal/m1/                   座位预约业务
  internal/m2/                   整室申请审批
  internal/m3/                   物业报修
  internal/common/               D 身份、资源、通知、审计等子域
  migrations/                    版本化 MySQL 迁移
  go.mod / go.sum                Go 模块与依赖版本校验
  各包中的 *_test.go             后端行为与模块测试
contracts/                        公开 HTTP 契约、错误码
infra/                            MySQL、应用运行和部署配置
scripts/                          构建、种子、发布、验收辅助命令
tests/                            跨模块 HTTP 集成与端到端测试
docs/                             需求、架构、过程与证据
```

MySQL 存储业务数据，模块按包和仓储边界隔离。D 是逻辑公共层，各子域按三组分工维护，单应用不改变责任归属。资源公共接口是唯一冲突仲裁入口；M2/M3 通过 HTTP 创建/移除来源阻塞，M1 的预约写入使用同一资源仲裁逻辑。整点小时预约建议采用小时槽唯一约束并配合事务锁，维修阻塞与整室占用仍需统一并发判定。

单应用中的 HTTP 调用仍不共享调用方的数据库事务。采用本地事务、outbox、幂等键、操作状态查询和重试；对外成功必须对应已确认的资源仲裁，后台补偿与失败状态可见。提醒调度支持可控时钟和幂等通知，便于验证时间边界。

先用 Docker Compose 运行 MySQL 和一个 Go + Gin 应用；期中取得服务器后迁移至实际测试环境，凭证在安全配置中管理。发布整个项目版本，使用部署锁协调迁移与集成验证；生产审批与回滚均需实际演练。

## 风险与验证

并发超卖用数据库冲突约束和并发测试验证；恢复覆盖来源用多工单/多来源测试验证；定时任务重复用幂等测试验证；RBAC 漏洞用越权与跨用户数据访问测试验证。接口不可用时测试重试与最终收敛，禁止靠 mock 掩盖集成失败。

## 单应用构建与发布要求

构建先安装锁定的前端依赖并执行 Vite build，将产物放入专用构建暂存目录，由 Go 的 embed 嵌入二进制并执行 go build，发布一个应用。嵌入目录和脚本待实现，不向业务源码目录复制文件。Gin 提供 /api 路由和静态文件，SPA 回退仅用于前端路径，不能把不存在的 API 返回成 HTML。生产无须运行 Vite 开发服务器。数据库独立运行，不把 MySQL 放入应用进程。CI 必须检查前端构建、后端行为及真实 HTTP 集成，任一步失败阻止后续部署。单应用发布覆盖三组模块，生产审批、版本标记和回滚要求不变。

## Go 后端配套要求

Gin 负责路由、中间件、参数绑定和响应，不默认提供完整权限、迁移或任务系统。MySQL 驱动、迁移工具、身份认证、日志和后台任务配套在骨架任务中比较与固定；接口输入需显式校验。数据库事务明确提交/回滚，HTTP 调用设置超时并传递 context，后台重试使用持久化操作记录。验证至少包含 go test ./...、适用的竞态检查、真实 MySQL 并发测试与 HTTP 集成，不能以语言切换取消原验收要求。前端脚本及依赖由锁文件固定，Go 依赖使用 go.mod/go.sum 管理。
