# 模块协作与集成开发

本文把模块分工转化为可执行的协作流程，适用于 M1/M2/M3 三个组及分摊的 D 公共能力。它是项目实施约定初稿，不是对课堂发言的逐字记录，也不代表已经完成联调。

## 1. 从分模块到完整系统

AI 可以生成代码，但三个组分别完成代码，不代表共同交付的系统可以正确运行。分模块的工程重点是明确边界、共同约定接口、处理失败和并发，并用真实集成验证最终效果。

| 场景 | 调用组 | 提供组 | 双方必须约定 |
| --- | --- | --- | --- |
| 整室批准占用座位 | M2 | M1 的资源接口 | 既有个人预约冲突策略、批准成功界点、到期与批准竞争 |
| 撤销整室申请释放占用 | M2 | M1 的资源接口 | 按申请来源释放、超时结果核对、重复释放 |
| 开始维修下架教室 | M3 | M1 的资源接口 | 阻塞何时生效、既有预约影响、失败和补偿 |
| 验收恢复教室 | M3 | M1 的资源接口 | 只解除本工单来源、多工单及整室占用共存 |
| 登录与权限使用 | M1/M3 | D 身份负责人（建议 M2） | 身份传递、动作权限、数据范围与撤权 |
| 业务通知 | M1/M2 | D 通知负责人（建议 M3） | 事件字段、收件人、去重、失败重试和过期抑制 |

业务效果见 [集成需求](../requirements/integration-and-decisions.md)，具体负责人见 [分工表](module-ownership.md)；本文件解释怎样协作完成这些要求。

## 2. 职责与代码边界

M2 决定申请是否完成合法审批，资源接口决定场地能否占用；不能先显示批准成功再忽略占用失败。M3 决定维修与验收流程，资源接口维护阻塞；不能把验收一张工单直接实现为“教室全部可用”。

每项公共能力由负责组实现、测试和维护，使用组负责自己的接入与业务限制。例如登录接口有缺陷由身份负责人修复，调用方错误使用接口由调用方修复。各模块只能通过公开契约改变其他模块状态，不直接写其数据表或调用内部仓储。

同仓库、单应用不取消模块边界。当前架构为 React + Vite、Go + Gin、MySQL；M2/M3 调用资源公开 HTTP 接口，满足课程真实网络调用演示。普通函数调用不能作为该验收证据。HTTP 调用不共享调用方数据库事务，调用前不得持有会阻塞接收端的资源锁，详见 [架构](../architecture/proposal.md)。

## 3. 先共同确认接口，再分别实现

提供组起草契约，调用组用真实业务案例评审，确认后按版本保存到 contracts/（目录和正式契约尚待骨架任务建立）。双方至少约定：

| 契约项 | 内容 |
| --- | --- |
| 请求 | 教室/座位 ID、带时区的起止时间、M1/M2/M3 来源、业务 ID、操作 ID和版本 |
| 身份 | 服务身份和权限范围；不能让调用方伪造任意模块来源 |
| 成功 | 什么已经持久化、是否确认生效；返回可核对的结果和来源标识 |
| 错误 | 输入错误、无权限、资源冲突、版本冲突、结果未知和依赖不可用分别表达 |
| 幂等 | 相同键同内容返回同结果，相同键不同内容拒绝；键保留期限需定义 |
| 查询与释放 | 能查操作是否生效；释放仅作用于自己来源，重复释放安全 |
| 时间与并发 | 区间边界、截止时间权威、最终成功界点、合法状态版本 |
| 追踪 | correlationId 串联业务、HTTP、资源写回与审计 |
| 兼容性 | 字段新增、废弃和不兼容变更的版本及迁移方式 |

示例：M2 请求“申请 A 占用教室 R 的 09:00–11:00”，资源端须在事务内检查整室与座位占用。返回成功意味着目标占用已确认；明确冲突意味着本次没有获得占用；请求超时则结果未知，需要核对。端点路径和 JSON 格式由正式契约确定，不能在各组代码里各自猜测。

使用方不能仅凭文档理解就认为契约可用；提供方也不能只测接口返回 200。至少有双方维护的成功、冲突、越权和重试契约测试。

## 4. 失败、并发与恢复的共同责任

- 请求超时不证明执行失败：调用组保存同一操作标识，查询或幂等重试；提供组保存可核对结果。
- 个人预约与整室审批竞争：由统一资源事务仲裁，禁止两个模块分别检查后各自写入。
- 已到期或撤销的申请：终态和来源版本防止迟到请求重新激活占用；双方对账并清理残留。
- 多张维修工单：每单有独立来源；释放一单后仍有其他阻塞就不可恢复。
- 业务与资源暂时失配：显示处理中、失败原因及可重试状态，不假装已成功；恢复任务重启后继续。
- 通知失败：重试投递，不重复审批、派单或取消；外部渠道不能无依据承诺严格一次投递。

提供组负责资源侧幂等、冲突和来源保护；调用组负责业务状态、操作记录、补偿与核对。任何一方单独实现都不能保证整条链路正确。

## 5. 联调步骤与验收证据

1. 双方先确定一个最小业务案例、契约和预期资源变化。
2. 各组先通过本模块行为测试，再在共享测试环境使用真实 HTTP 与 MySQL 联调。
3. 验证成功链路后验证冲突、无权限、重复请求、响应丢失、进程重启和迟到请求。
4. 保存该次测试的版本、输入、业务 ID、操作 ID、关联日志、实际数据库/搜索结果和断言；遮蔽凭证及个人数据。
5. 故意破坏关键检查，确认对应测试失败，恢复后重新执行；不能模拟掉被测资源逻辑。

| 验收场景 | 必须观察到的结果 |
| --- | --- |
| M2 批准目标区间 | M1 搜索排除对应座位，直接提交预约也拒绝；区间外仍可用 |
| M2 与个人预约并发 | 不双占，失败方得到明确结果 |
| M3 开始维修 | 全室下架；不能通过绕过搜索直接预约 |
| 两张工单只验收一张 | 另一工单阻塞保留；全部验收后仍检查 M2 和管理员停用 |
| 写回成功但响应丢失 | 核对后收敛；无重复占用、通知或错误业务终态 |
| 服务在写回后重启 | 持久化记录驱动恢复，不能依赖内存保存结果 |

各组测试通过不等于集成通过。mock 可帮助隔离部分单元测试，但不能替代以上网络集成。当前只有规划文档，尚未运行这些场景。

## 6. 给 AI 的任务怎么拆

先由参与组理解和评审方案，再分别交给 AI 明确任务。一个任务应包含：需求 ID、负责模块、允许改动目录、已确认契约、禁止改动范围、状态与失败规则、验收场景。不要只说“把三个模块做完”。

以 INT-01 为例，按依赖拆分：

| 阶段 | 主责 | AI 任务范围与验收 |
| --- | --- | --- |
| 契约设计 | M1/M2 共同 | 提出字段、成功界点、错误和恢复方案；人工比较并确认 |
| 提供端实现 | M1 | 实现统一占用、释放和结果查询；并发及来源测试通过 |
| 调用端实现 | M2 | 实现最终审批、状态确认、操作持久化与重试；不改资源内部表 |
| 联调 | M2 牵头、M1 配合 | 真实 HTTP 测试批准、冲突、超时与恢复，记录证据 |
| 评审与合并 | 双方 | 检查契约兼容、schema 变更与测试，再人工验收；冲突由人处理 |

临时模拟接口可支撑开发，但必须显式记录依赖与待联调状态。跨模块或公共变更经使用组评审；不兼容修改先更新契约和任务，再协调发布。开发证据保留在版本历史与实际测试结果中，不伪造过去的决策或验收。
