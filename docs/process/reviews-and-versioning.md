# Review 与版本流程

用户补充：第 7 周开始 3 次 review，期末 3 次 review；具体日期未提供，不推算为已确定日历。期末展示可能采用录屏，应保持可现场演示并保留真实操作记录。

| 检查点 | 建议证据 |
| --- | --- |
| 第一轮 1 | 分工与公共层候选；需求基线；架构比较；协作规则 |
| 第一轮 2 | 可运行骨架；SQL 迁移与种子；首个 M1 闭环；CI 结果 |
| 第一轮 3 | M2/M3 细化；跨模块契约；主要风险与行为测试 |
| 期末轮 1 | 全部主功能与网络集成；来源追溯；失败重试验证 |
| 期末轮 2 | 空环境部署；迁移演进；生产审批和回滚 |
| 期末轮 3 | 最终演示与真实人机协作过程、伦理问题、未完成项 |

以上为建议材料分配，不替代课程实际 review 通知。

使用 main + 短期功能分支和 PR；命名示例 feat/M1-01-seat-booking。每项提交对应需求 ID、问题与验证结果。文档、规则、迁移、流水线一起随迭代提交，不集中补历史。不要制造过去的日期或虚构人工验收。

AI 先提供可审查方案与变更，再由成员人工验收后提交。代码冲突交由人处理。公共层、schema 与跨模块变更须组内评审。当前文档未提交，不能将文件生成描述为已有提交历史。

部署用 tag 关联 commit；测试失败阻止后续阶段；测试环境统一部署所有模块，生产人工批准。数据库破坏性迁移可能无法单靠旧镜像回滚，应先采用兼容性迁移并演练数据备份恢复。
