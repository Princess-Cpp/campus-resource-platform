# 校园资源服务平台：任务拆解与候选实施方案

状态：根据 Pj-任务书.pdf 整理的提案；尚未经过组内评审，未声明功能已实现。

## 1. 需求与验收基线

| ID | 范围 | 验收行为 |
| --- | --- | --- |
| D-01 | 身份与 RBAC | 未登录请求被拒绝；学生不能审批或派单；管理员权限可配置；院系空间仅对所属院系开放 |
| D-02 | 空间与座位 | 管理员维护教室、开放时间、座位唯一编号和插座标记；停用资源不允许新预约 |
| D-03 | 通知与审计 | 每次重要状态变化记录操作者、时间、资源与来源；通知失败可重试且不重复发送 |
| M1-01 | 搜索与预约 | 按空间、时间和插座筛选；预约以整点小时为单位，默认最长 4 小时且可配置；并发重叠预约只能一个成功 |
| M1-02 | 签到 | 教室每日动态编码绑定教室和日期；错误、过期、其他教室编码不能签到 |
| M1-03 | 提醒与违约 | 开始前 15 分钟提醒；开始后 10 分钟未签到再次提醒；15 分钟后取消、释放、通知并记录一次违约；重试不重复记录 |
| M1-04 | 历史与统计 | 学生仅查询本人记录；历史复用仍检查当前可用性；运营权限可查预约和利用率 |
| M2-01 | 申请与审批 | 验证申请权限；提交后按配置顺序逐级审批；越权、跳级、重复审批均被拒绝 |
| M2-02 | 驳回与超时 | 驳回或超时后进入终态；释放本申请产生的占用；定时任务可幂等重跑 |
| M3-01 | 工单流程 | 上报、派单、维修中、完工待验收、验收与评价具备明确权限和合法状态迁移 |
| M3-02 | 超时升级 | 到期升级并通知；重试不产生重复升级；验收拒绝后按明确策略返回维修 |
| INT-01 | M2 → M1 | 审批通过后，时间区间内全室座位不可个人预约；审批与个人预约并发也不得双占 |
| INT-02 | M3 → M1 | 存在维修中工单时全室下架；验收通过仅移除此工单的阻塞，其他维修阻塞仍有效 |
| INT-03 | 状态追溯 | 每项占用或下架保留 M1/M2/M3 来源及业务记录 ID；释放某来源不能清除其他来源 |
| ENG-01 | 迁移与种子 | 空数据库一次重放到最新结构；重复启动不重复迁移；种子幂等且与业务数据分离 |
| ENG-02 | 交付 | PR 与提交触发构建测试；测试失败阻止部署；全组模块统一部署测试环境；生产审批、版本追溯和回滚 |
| ENG-03 | 人机协作 | 规则、任务约束、决策、需求实现与验证映射纳入版本管理；人工验收后提交；代码冲突交由人处理 |

M2/M3 的审批层级、超时策略、申请门槛、维修期间已有预约处理及个人预约与整室申请冲突策略已在 docs/requirements/ 中给出细化提案，仍待业务评审确认。

## 2. 架构候选与建议

用户最新选择：前端 React + Vite，后端 Go + Gin，SQL 数据库 MySQL；同仓库、单应用部署已确认。技术栈按用户选择记录，不虚构组内评审结果。Go、Gin、React 和 Vite 的版本待固定；MySQL 8.4 LTS 为版本提案。

React 负责界面，Go + Gin 负责服务端业务；用户已确认同仓库、单应用部署，由 Go + Gin 提供前端构建产物；前后端仍使用各自框架。会话、通知、定时任务、幂等与业务数据使用 MySQL 持久化。

同仓库、单应用部署：前端 frontend/，后端 backend/ 按 M1/M2/M3/D 划分逻辑模块；Go + Gin 提供前端产物。M2/M3 通过同应用公开 HTTP 资源接口写回，不直接改写 M1 数据表，也不把函数调用当作网络集成证据。详见架构文档。

核心不变量：统一资源冲突仲裁；时间区间使用 [start,end)；所有时间处理明确时区；幂等键和来源记录独立存储；回滚与恢复按来源移除；事务和重试覆盖竞态。审批占用必须与个人预约共享冲突判定。跨服务写回采用幂等请求和可重试投递，失败不能显示虚假的最终成功。

## 3. 迭代与验证

1. 项目启动：确认模块归属；提出公共层治理方案；补全业务规则与需求基线；记录架构候选及风险；建立 AGENTS.md 和任务验收模板。
2. 可运行骨架：前后端、数据库迁移、幂等种子、身份权限、空间主数据、容器启动、CI；验证空环境启动和越权拒绝。
3. M1 纵向闭环：搜索、预约、签到、历史、提醒与违约；验证重叠并发、时间边界、编码绑定、任务重试。
4. M2/M3 集成：状态机、审批和报修；公开接口写回；验证部分重试、多工单、恢复不覆盖其他来源和跨模块竞态。
5. 交付：测试环境自动部署、生产人工审批、迁移串行锁或部署窗口、版本显示与回滚演示；对关键实现执行故意破坏验证测试确实失败。
6. 可选扩展：DSH 业务代理；仅调用公开接口；缺少时间或区域时追问；不能替代前述任何验收。

每次迭代应是可人工审查的变更，不自动制造已评审记录，不替用户提交或合并。未实现条目持续保留状态及验证映射。

## 4. 工程伦理与真实决策

最小化学生个人信息收集；历史与违约数据访问隔离；审计日志避免保存密码或签到编码；明确数据保留期限。讨论预约公平性、误判违约的申诉与纠正、无障碍体验、通知可靠性、维修造成的预约影响。个人论文只能记录成员实际参与的工作，不能虚构组内一致或实践经历。

## 5. 外部前提

组员和模块负责人与公共层归属需由项目组决定。测试/生产服务器、域名、证书、部署权限、通知渠道凭证尚未提供；可先用本地容器和开发邮件接收服务验证，不宣称已部署测试或生产。凭证通过安全环境配置提供，不写入仓库或聊天。
